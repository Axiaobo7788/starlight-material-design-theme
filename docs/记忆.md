# 仓库记忆

> 这里记录跨多次会话、跨多个 coding agent 都应该保留的长期事实。  
> 它不是 changelog，也不是 TODO 列表。短期状态请看 `docs/进度.md`。

## 项目目标

`starlight-theme-md3` 的目标不是把 Starlight 替换成一套新的 Material 组件框架，而是在 **尽量保留 Starlight 原生结构、行为和可访问性** 的前提下，把高影响视觉层与交互层调整为 Material Design 3 / Material You 风格。

核心判断标准：

- 看起来像 MD3；
- 仍然像一个高信息密度文档站；
- 不破坏 Starlight 原本擅长的导航、搜索、内容、TOC 和 MDX；
- 用户接入方式尽量保持简单。

## 架构记忆

### CSS-first

主题优先通过：

- CSS custom properties
- cascade layers
- token mapping
- 少量 client runtime

实现。

只有在浏览器原生控件或 Starlight DOM 无法满足视觉/交互要求时，才使用小型 Astro override。

典型例子：`ThemeSelect.astro`。

### Token-first

视觉代码必须优先依赖：

- `--md-sys-color-*`
- `--md3-comp-*`
- shape / state / motion tokens

不要在组件 CSS 中到处写孤立 raw color。

### Starlight 仍是主体

以下能力继续由 Starlight / Astro 提供：

- content model
- router
- search/Pagefind 基础能力
- table of contents
- MDX/components
- accessibility semantics

本主题不应该为了视觉一致性重写这些基础设施。

## 明确拒绝的方向

长期不要默认引入：

- Tailwind 作为核心依赖；
- `@material/web` runtime；
- 大规模 Material Web Components 重构；
- glass / backdrop blur 作为主要视觉语言；
- glow；
- 渐变替代 tonal surface；
- 大量 heavy shadow；
- 所有组件都做成 full pill；
- landing page 式超低信息密度。

Material Web 可以作为组件 anatomy、token、motion、state 的设计参考。

## 色彩与层级记忆

项目曾经尝试 canonical purple，但人工复核认为默认示例容易呈现单一 lavender-gray 感。

因此默认演示与 fallback 更偏向：

- teal tonalSpot
- seed `#00a99d`

重点不是“青色比紫色正确”，而是 **primary / secondary / tertiary / neutral surface 的角色关系要读得出来**。

当前长期规则：

- page/article：surface
- chrome：surface-container 类角色
- persistent navigation：secondary-container / on-secondary-container
- primary：高强调 action、link、focus、轻量 active indicator
- TOC：保持安静，不变成主导航
- dark mode：避免 pure black

## Motion 记忆

项目不追求“动画越多越高级”。

允许并认可：

- pointer-origin ripple
- state transitions
- menu open/close
- drawer / TOC disclosure
- short navigation pending feedback
- TOC continuity
- restrained homepage entrance motion
- reduced-motion fallback

避免：

- 普通页面大规模 reveal
- hover lift / transform 滥用
- decorative shimmer
- scroll spectacle
- 无依据的弹簧动画

## Runtime color picker 记忆

从 0.2.2 起，runtime color picker 已经是实际功能，不再只是设想。

它是 opt-in 的，不应该影响默认未启用路径。

支持 author / visitor / both 等模式，并可选持久化 visitor palette。

曾经研究过读取系统 accent，但浏览器返回值可能是隐私保护后的固定 system color，无法可靠代表用户真实系统强调色，所以该来源已经移除。

后续 agent 不要重新把“读取真实 OS accent”当成已有可靠能力。

## Theme menu 记忆

原生 `select` popup 无法可靠做出一致的 MD3 menu，尤其会暴露系统 selected blue。

因此项目接受了一个小型 `ThemeSelect.astro` override。

长期方向：

- top app bar trigger 低强调；
- menu 是临时 surface；
- extra-small/small shape；
- selected state 安静；
- trailing checkmark；
- 不把 menu item 做成一排 pill。

## TOC 记忆

TOC active state 已经过多轮视觉复核。

最终方向是：

- 单一 floating tracker；
- 小型 vertical pill；
- 保持轻量；
- static fallback 用于 no-motion / fallback 情况。

曾被否决的方向包括过于方块化、badge 化、像主导航一样抢眼的 tracker。

## Homepage 记忆

曾经尝试让首页更像普通 docs chrome，虽然视觉 reviewer 可接受，但人工复核认为它太像普通文档文章。

因此后来恢复/保留 splash 方向。

这是一个典型原则：**自动视觉 reviewer 的通过不是最高优先级，人工产品判断可以 supersede 它。**

## Reviewer / implementer 分工

历史设计流程中：

- Gemini 3.1 Pro：主要作为 MD3 visual reviewer / patch spec reviewer；
- Codex：主要作为实现、测试、仓库集成 agent。

这个分工不是强制工具依赖，但体现了一个重要工作方式：

> 视觉判断与仓库实现尽量分离，避免一次 agent 既自由重设计又自由重构代码。

## Package / release 记忆

当前核心 runtime dependency 应保持很少。

发布前必须关注：

- package exports
- README assets
- Chinese README
- package-consumption fixture
- `pnpm pack --dry-run`
- peer dependency 范围
- GitHub Pages demo
- screenshot regression

不要未经明确要求：

- bump version
- 创建 tag
- publish npm
- 扩大 peer range

## 测试记忆

依赖维护不是“能安装就算成功”。

至少应关注：

- typecheck
- contrast
- build
- package-consumption
- pack dry-run

视觉/交互相关修改必须关注 Playwright screenshot regression。

如果 screenshot 失败：

1. 先判断 DOM / CSS / rendering 是否真的发生预期变化；
2. 排除上游依赖导致的意外偏移；
3. 只有确认新视觉是接受的，才更新 baseline。

不要用“update snapshots”掩盖回归。

## 文档维护记忆

仓库内部文档存在两种不同寿命：

### 经常更新

- `docs/进度.md`
- release checklist
- compatibility / current validation

### 长期稳定

- `docs/记忆.md`
- `docs/design/DECISIONS.md`
- `docs/design/TOKEN_CONTRACT.md`

如果实现与旧文档发生冲突，应以当前源码 + 测试 + 已接受决策核对后修正文档，而不是让旧文字反过来约束已经完成并发布的功能。

## 当前已知文档历史问题

截至 2026-11-02，至少出现过：

- implementation overview 仍写 runtime color picker 未包含；
- release checklist 仍停留在首次 0.1.0 发布语境。
